# erl：编程领域的 efficient RSI

目标：在同样的 GPU 占用小时下，让自我改进搜索把评估花在会影响选择的地方。所有策略先在已有 9 个 run 的账本上离线回放，不用 GPU；回放结果站得住，再接进 HGM 在线跑。

| 文件 | 作用 |
| --- | --- |
| `policy.py` | 停止策略的接口：每次要评估某个节点之前，决定继续评估还是让它退出。已有：不停止、每个节点最多评 N 题（`FixedCap`）、决策感知的动态阈值（`UcbVsIncumbent`：节点的上界低于当前最优的 Beta 下界就退出） |
| `replay.py` | 在账本上按到达顺序重放每个节点的搜索题结果，统计省下的评估时间，以及在同样 GPU 小时截断点、同样选择规则（Beta 下界，eps 0.05）下，最终选出的 agent 是否改变 |
| `micro_stop.py` | 单题早停（EarlyEval 式）：分类器只用本次搜索里已经结束的评估在线训练；被停下的评估记为未解出，改写后的结果流再交给 `replay.py`，看最终选择是否改变。对照组是更低的超时上限 |
| `predict_stop.py` | 预测驱动的早停，边搜索边迭代：预测器根据 diff、父代当时的成绩、深度和前 k 题的结果与耗时，预测子代最终的解出率，作为 Beta 先验（强度 w）加进子代的后验；每多 50 个结果用当时已观察到的结果重训一次。w 可以固定，也可以在线校准（`auto`） |
| `online_stop.py`、`test_online_stop.py` | 在线版本：hgm.py 在 `HGM_ERL_STOP=1` 时调用；以及从已有 run 导出预测器历史数据（`dump-history`） |
| `predict_robust.py` | 预测早停的稳健性检查：每个节点的结果在自己的评估时间点之间随机打乱（时间戳留在原位），比较纯统计、w = 5、自动 w，以及自动 w 叠加单题有条件超时 |
| `test_replay.py`、`test_micro_stop.py`、`test_predict_stop.py` | 单元测试 |

计划中的模块：`proxy.py`（小模型代理的配对评估、在线回归和 conformal 下界）。

## 运行

```bash
python -m unittest test_replay -v
python replay.py --ledger ../runs/ledger.jsonl --output-root ../repos/HGM/output_hgm \
    --runs hgm-fixed-r0 hgm-orig-r0 dgm-r0 --max-hours 9.646 [--rows-out rows.jsonl]
```

不停止时的选择会和 `final_eval/final_result.json` 里的 `best_node` 对照，不一致会打印 WARNING。

## 回放的局限

- 省下的时间在真实搜索里会被用来评估别的节点，回放看不到这部分收益或代价。
- HGM 选父代时也用到后代的评估结果；退出的节点结果变少，之后长出的子代可能不同。
- 策略只能在结果之间做决定。DGM 一次评一批（先 10 题，过门槛再评更多），回放只能在批与批之间停。

## 第一次结果（2026-11-01，9 个 run，截在 9.646 GPU 小时）

9 个 run 不停止时的选择都和 final_eval.py 一致。

| 策略 | HGM 6 个 run 省下的评估时间 | 选择改变的 run | DGM 3 个 run |
| --- | --- | --- | --- |
| 每个节点最多 10 题 | 40.8–54.2% | 6 个里 5 个 | 0–19%，选择不变 |
| 每个节点最多 20 题 | 5.2–18.3% | 6 个里 2 个 | 0 |
| 上界 80%（ucb0.2），至少 3 题 | 6.1–23.5%，平均 15.1% | 0 | 0 |
| 上界 90%（ucb0.1），至少 3 题 | 1.2–8.7% | 0 | 0 |
| 上界 95% 及以上 | 0–1.8% | 0 | 0 |

- 固定题数要么省得多但选错，要么省得少；按和当前最优的距离决定停不停，能在选择不变的前提下省 6–24%。
- DGM 本身已经是"先评 10 题、过门槛再评"的两段式，按批停没有空间；要省只能在批内逐题停，需要在线实现。

## 稳健性检查（200 种结果顺序）

回放只有一种结果顺序，结论可能是运气。这里把每个节点自己的结果在它的评估时间点之间随机打乱（哪个节点在什么时候被评估不变，只改变它先拿到哪个结果），重放 200 次。截断点处每个节点的全部结果不变，所以不停止时的选择不变，选择的变化只来自策略。

"损失"是新选出的节点和原选择相比，在全部搜索结果上的解出率低多少个百分点（负数表示更好）。全部结果本身也有噪声，这个损失只能说明新选择是不是明显更差。

| 策略 | 省下的评估时间 | 选择改变的顺序比例 | 损失（百分点） |
| --- | --- | --- | --- |
| 每个节点最多 10 题 | 33.5–46.0% | 32–84% | −2.1 到 +8.9 |
| 每个节点最多 20 题 | 4.1–15.5% | 3–75% | +0.3 到 +2.7 |
| 上界 80%（ucb0.2），至少 3 题 | 12.9–33.3%，平均 17.6% | 0–18% | 0 到 +0.3 |
| 上界 90%（ucb0.1），至少 3 题 | 3.4–15.9% | 0–8% | 0 到 +0.1 |
| 上界 95% 及以上 | 0.1–6.4% | 0–3% | 0 |

- ucb0.2 在一部分顺序下会换掉选出的节点，但换上的节点全部结果几乎一样好（最多差 0.3 个百分点），远小于单遍评估约 3.9 个百分点的随机误差。
- 固定题数换掉选择时，损失可以到 9 个百分点。
- 结论：上界 80% 的动态阈值可以作为在线实验的默认设置，能腾出约 1/6 的评估时间。

## 单题早停（2026-11-01，6 个 HGM run）

`micro_stop.py` 的两类设置：`cap<C>` 把超时上限从 3600 秒降到 C 秒；`f<f>-after<m>` 在运行满 m 秒后，一旦分类器给出的"会失败"概率 ≥ f 就停。分类器每多 100 次评估重新拟合，评估开始前只能用已经结束的评估。DGM 一次报一批结果，单题结果改不了，所以不在内。

| 设置 | 单题早停省下的评估时间 | 被停的评估里本来能解出的 | 选择不变的 run | 叠加 ucb0.2 后总共省下 | 叠加后选择不变 |
| --- | --- | --- | --- | --- | --- |
| 不早停 | 0 | 0 | 6/6 | 6.1–23.5% | 6/6 |
| 超时降到 2400 秒 | 11.9–17.1% | 2–12 次 | 4/6（损失 −0.8、+2.3） | 21.5–32.4% | 4/6 |
| 超时降到 1800 秒 | 20.1–28.8% | 6–14 次 | 4/6 | 31.0–38.5% | 4/6 |
| 分类器 f0.95，满 1200 秒后 | 0.1–17.9% | 0–4 次 | 6/6 | 6.8–36.0% | 6/6 |
| 分类器 f0.95，不限时间 | 0.3–30.2% | 1–11 次 | 4/6（损失 +0.8、−0.8） | 6.9–43.4% | 4/6 |
| 分类器 f0.97 及以上 | 0–15.8% | 0–6 次 | 5/6 及以上 | 6.1–33.1% | 5/6 及以上 |

- 直接降低超时上限省得多，但会砍掉一部分慢慢做对的运行（每个 run 2–14 次），6 个 run 里有 2 个选择因此改变，其中一个变差 2.3 个百分点。
- 分类器很保守：在线训练的数据少（每个 run 只拟合 4–7 次），多数 run 里很少有把握到 0.95，只有 hgm-fixed-r1 省得多（17.9%）。"满 1200 秒后才停"在 6 个 run 里都不改变选择。
- 最稳的组合是 f0.95-after1200 加 ucb0.2：6 个 run 选择都不变，省下 6.8–36.0%。

### 有条件的超时

`cap<C>-if<g>`：运行到 C 秒时问一次分类器，"会失败"的概率 ≥ g 才停，否则跑到原来的 3600 秒。分类器还没训练出来时不停。

| 设置 | 单题早停省下 | 被停下但本来能解出的 | 选择不变 | 叠加 ucb0.2 后共省（平均） | 叠加后选择不变 |
| --- | --- | --- | --- | --- | --- |
| **1800 秒，g = 0.9** | 5.3–14.0% | 1–5 次 | **6/6** | **11.2–33.1%（22.2%）** | **6/6** |
| 1800 秒，g = 0.7 或 0.8 | 14.2–19.6% | 2–10 次 | 4/6 | 23.0–36.0% | 4/6 |
| 2400 秒，g = 0.9 | 3.9–8.6% | 1–3 次 | 5/6 | 10.0–29.3% | 5/6 |
| 2400 秒，g = 0.7 或 0.8 | 8.3–11.5% | 2–6 次 | 4/6 | 15.5–31.1% | 4/6 |
| 对照：分类器 f0.95，满 1200 秒后 | 0.1–17.9% | 0–4 次 | 6/6 | 6.8–36.0%（19.3%） | 6/6 |

- 1800 秒、g = 0.9 是目前最好的单题设置：选择都不变，叠加后平均省 22.2%，最低也有 11.2%（f0.95-after1200 最低只有 6.8%）。
- 改变选择的总是 hgm-orig-r0 和 hgm-fixed-r2。hgm-orig-r0 选出的节点只有 7/17 的记录，它的选择取决于很少几道题，2400 秒、g = 0.9 停掉的几次能改变选择，1800 秒、g = 0.9 停掉的却没有。说明在这类 run 里，"选择变不变"本身就很脆弱，在线实验需要多跑种子。
- 在线实验的默认设置：子代级 ucb0.2（至少 3 题）+ 单题 1800 秒、g = 0.9 的有条件超时。

## 预测驱动的早停（2026-11-01，6 个 HGM run）

`predict_stop.py`：子代的后验是 Beta(1 + 做对 + w·p̂, 1 + 做错 + w·(1 − p̂))，p̂ 是预测器给的最终解出率，上界低于当前最优的 Beta 下界就停。最终选择仍然只看真实结果。预测器每 50 个结果重训一次，只用当时已观察到的结果做标签；`--history` 另外用更早结束的 run（包括 3 个 DGM run）的记录训练。下表都是 80% 上界、至少 3 题。

| w | 历史数据 | 省下的评估时间（平均） | 选择不变 | 预测误差（前 3 题时，MAE） |
| --- | --- | --- | --- | --- |
| 0（纯统计，对照） | — | 6.1–23.5%（15.1%） | 6/6 | — |
| 5 | 无 | 10.3–39.9%（25.4%） | 6/6 | 0.10–0.14 |
| 5 | 有 | 13.4–42.0%（28.0%） | 6/6 | 0.06–0.12 |
| 10 | 无 | 11.1–86.2% | 4/6 | 0.10–0.14 |
| 20 | 无 | 25.2–89.2% | 1/6 | 0.11–0.16 |
| auto | 无 | 11.6–32.5%（21.4%） | 6/6 | 0.09–0.13 |
| auto | 有 | 10.6–34.9%（26.3%） | 6/6 | 0.05–0.11 |

- 预测有用，但只在权重合适时：w = 5 比纯统计多省约 10 个百分点，选择都不变；w ≥ 10 时预测器区分能力不够却被过度信任，几乎所有子代都被停掉（省 80–90% 是假的节省），选择也变了。
- 历史数据把前 3 题时的预测误差从 0.10–0.14 降到 0.05–0.12，节省也随之增加。这和 EarlyEval 的做法一致：同一基准上已有的带标签记录很有价值。
- 在线校准 w（`auto`）第一版失败：用子代全部结果做标签时，被预测停掉的子代只剩导致它被停的那几个结果，预测看起来很准，w 被推到上限，停得越来越多。改为只用预测之后才拿到的结果做标签（样本外），被停掉的子代自然不参与校准，6 个 run 选择都不变。
- 自动 w 常常顶到上限 10。它和固定 w = 10 的区别是：前期标签不够时 w = 0，等预测器在本次搜索中证明过自己才加权。
- 尚未做：在线验证。

### 稳健性检查（20 种结果顺序，`predict_robust.py`）

都是 80% 上界、至少 3 题、带历史数据。6 个 run 各 20 种顺序，共 120 种。叠加单题超时时，单题早停只按原始顺序判一次（它的分类器按真实时间线训练），被停下的结果随所在的位置一起打乱。

| 设置 | 随机顺序平均省下（各 run 范围） | 选择改变的顺序 | 平均损失 | 最大损失 |
| --- | --- | --- | --- | --- |
| 纯统计（w = 0） | 17.5%（11.8–33.9%） | 4/120 | −0.02 | 0 |
| w = 5 | 30.9%（21.5–54.2%） | 12/120 | +0.10 | +6.7 |
| **自动 w** | **27.7%（19.3–45.7%）** | **9/120** | **+0.08** | **+2.3** |
| 自动 w + 单题 1800 秒、g = 0.9 | 35.1%（25.2–47.4%） | 20/120 | +0.55 | +8.4 |

第一轮（上表）里各设置用的是不同的随机顺序，设置之间的差别混进了顺序的运气。第二轮（`runs/erl_predict_robust2.txt`）改为所有设置共用同一组 20 种顺序（每种顺序一个种子），并加了叠加方式的变体：

| 设置（第二轮，共用顺序） | 随机顺序平均省下（各 run 范围） | 选择改变的顺序 | 平均损失 | 最大损失 |
| --- | --- | --- | --- | --- |
| 纯统计（w = 0） | 17.2%（13.1–31.8%） | 7/120 | +0.04 | +2.3 |
| w = 5 | 32.0%（22.9–51.0%） | 22/120 | +0.36 | +8.4 |
| 自动 w | 27.4%（17.7–42.9%） | 13/120 | +0.24 | +8.4 |
| 自动 w + 单题 1800 秒、g = 0.9 | 34.1%（25.3–47.1%） | 12/120 | +0.25 | +8.4 |
| 自动 w + 单题 1800 秒、g = 0.95 | 29.2%（18.2–44.5%） | 13/120 | +0.24 | +8.4 |
| 同上 g = 0.9，被停的结果不进预测器标签 | 33.4%（24.3–46.8%） | 12/120 | +0.26 | +8.4 |
| 同上 g = 0.9，被停的结果既不进标签也不进停止判断 | 29.9%（20.4–43.4%） | 9/120 | +0.19 | +8.4 |

- 更正第一轮的结论：在同一组顺序上，叠加单题超时并不增加选错（12/120 对自动 w 单独的 13/120），多省约 7 个百分点。第一轮"选择改变翻倍"主要来自两组设置用了不同的顺序。
- 所有预测设置的 8.4 个百分点最大损失都出在 hgm-orig-r1 的同一批顺序上（自动 w 3/20，平均损失 1.26）：预测器在这些顺序里把真正的最优节点过早停掉。纯统计在这些顺序下没有选错。所以预测确实带来了少量大损失的风险，概率大约是每个 run 几十分之一到十分之一，20 种顺序还不足以精确估计。
- 固定 w = 5 选错最多（22/120），不推荐。
- 把被单题停下的结果排除在预测器标签之外几乎没有影响；同时排除在停止判断之外更稳（9/120）但少省约 4 个百分点。g = 0.95 比 g = 0.9 少省约 5 个百分点，选错也没减少。
- 在线实验（`hgm-erl`，见下）先只开自动 w 的节点停止，不叠加单题超时：先单独验证节点停止在线是否成立，单题超时作为下一组。

## 在线实验（2026-11-02 开始）

`online_stop.py` 是 `predict_stop.py` 的在线版本，hgm.py 在 `HGM_ERL_STOP=1` 时调用它（默认关闭，原有配置不受影响）：

- 选下一个要评估的节点时，排除被停掉的子代；被停的子代仍留在树里，可以作为父代。
- 子代创建时读它的 `model_patch.diff` 算 diff 特征；每次评估结束把结果和耗时交给停止器；每 50 个结果重训预测器并重新校准 w。
- 预测器的历史数据：`runs/erl_history.json`，原始实验里来自已有 9 个 run（截在 9.646 GPU 小时）的 3802 行。它是运行产物，不在 git 里，用 `python online_stop.py dump-history --ledger ... --prescreen-rows ... --runs ... --out ../runs/erl_history.json` 从自己跑完的 run 生成；没有这个文件时，`run_all.sh` 让预测器只用本次搜索的数据训练。
- 停止和重训都记进账本（`erl_retire`、`erl_fit`）；停止器内部出错只记 `erl_error`，并当作"继续评估"，不会中断搜索。
- `test_online_stop.py` 检查在线停止器和离线回放在同一结果流上停掉的节点和省下的时间完全一致。

运行：`CONFIGS=hgm-erl REPEATS="0 1 2" BUDGET=1100 ./run_all.sh search`。预算设 1100 次评估，是为了保证跑满 9.646 GPU 小时（已有 HGM run 在这个时间内做了 612–784 次评估）；之后用 `CONFIGS=hgm-erl FINAL_HOURS=9.646 ./run_all.sh final` 截在同样的 GPU 小时做最终评估，和 hgm-fixed 比较。

### 和父代配对的特征（`--only ... paired`，`runs/erl_predict_paired.txt`）

借鉴"在新旧任务上评测"：子代已评过的题里，父代做对而子代做错的有几道（改坏的），父代做错而子代做对的有几道。根节点的逐题结果取自 `initial_polyglot/default_agent/metadata.json`。同样 20 种顺序 × 6 个 run：

| 设置 | 平均省下 | 选择改变 | 平均损失 | 前 3 题时 MAE |
| --- | --- | --- | --- | --- |
| w = 5 | 32.0% | 22/120 | +0.36 | 0.078 |
| w = 5 + 配对 | 32.1% | 20/120 | +0.25 | 0.078 |
| 自动 w | 27.4% | 13/120 | +0.24 | 0.077 |
| 自动 w + 配对 | 27.3% | 13/120 | +0.24 | 0.077 |

- 没有改善：预测误差和节省几乎不变。前 3 题里平均只有不到 1 道是父代做对的题（父代解出率约 17–30%），早期配对信息太少；评得多时子代自己的解出率已经包含了同样的信息。
- 配对特征保留为可选项（`paired=True`），默认关闭。

### 在线审计（`online_stop.py`，默认关闭）

借鉴"回滚"：在线时离线回放无法知道停得对不对。审计让一部分（`HGM_ERL_AUDIT`，按子代 id 的哈希选，可复现）本该停掉的子代再评 `HGM_ERL_AUDIT_N` 题，然后只看真实结果判断：子代的后验均值 (1 + 做对) / (2 + 题数) 不低于其他节点中当前最优的解出率，就是"停错"（它可能参与竞争），子代恢复评估；否则确认停掉。审计满 5 次、停错率超过 20% 时，w 的上限减半，逐步退回纯统计。

判定标准试过两种（`audit_offline.py`，已有 6 个 HGM run，所有停止都审计，不回滚）：

| 标准 | 再评题数 | 纯统计的停错 | 自动 w 的停错 |
| --- | --- | --- | --- |
| 上界回到当前最优的下界之上 | 5 | 19/20 | 28/36 |
| 后验均值不低于当前最优的解出率（采用） | 5 | 0/20 | 1/36 |
| 同上 | 10 | 1/13 | 1/18 |
