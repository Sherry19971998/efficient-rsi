计算高效的编程智能体自我改进：代码导读与开放方向

组会材料 · 2026 年 11 月。环境搭建和运行步骤见仓库根目录的 README.md。

1. 研究问题

项目说明
研究对象递归自我改进（recursive self-improvement, RSI）的编程智能体，如 DGM [2] 和 HGM [1]。智能体反复改写自己的代码，在编程题上评估新版本，保留表现好的版本。
成本来源主要是评估。每道题都在独立的 Docker 容器中运行：智能体调用大模型解题，再运行测试。解题时间上限 1 小时（HGM 论文附录 C.1 [1]，配置项 evaluation_timeout），测试上限 2 分钟。
研究目标模型固定，只改进搜索与评估策略，把有限的评估预算分配给真正影响最终选择的候选。
评价标准在相同的 GPU 占用小时下，最终选出的智能体在留出题上的准确率。

2. 实验设置

项目设置依据
基准Polyglot [3]，225 道题、6 种编程语言；59 道用于搜索，166 道留出留出题不参与搜索中的任何决策，其上的准确率是无偏估计
模型Qwen3-Coder-30B-A3B（FP8）[4]，在一张 H100 上用 vLLM 部署与 HGM 论文的 Polyglot 设置一致
比较口径所有方法统一截在 9.646 个 GPU 占用小时，并在预算的 1/3、2/3 处各评估一次（./run_all.sh checkpoints）等成本比较（compute-matched comparison）。预算在看到结果之前固定，取自第一轮最短的运行
搜索时长每次搜索运行 10.5 小时后停止保证每次运行都超过截断点的工程余量；搜索策略本身不读取这个上限，截断不改变搜索行为
最终选择在截断点上，选搜索成绩 Beta 后验 5% 分位数最高的节点所有方法使用同一条规则（instrumentation/results.py）
重复次数每种配置 3 次独立运行，用自助法（bootstrap）给出置信区间instrumentation/compare.py

为什么不报告搜索成绩：从大量带噪声的估计中选最大值，选中的往往是被高估的那个（赢家诅咒，winner's curse）；而且搜索过程一直针对这 59 道题优化。因此搜索成绩只用于决策。为什么按 GPU 小时而不按评估次数比较：HGM 异步调度，GPU 持续有负载；DGM 按代同步，等待期间 GPU 空闲，相同评估次数下占用 GPU 的时间明显更长。

口径的局限：GPU 占用小时按墙钟时间计，会受服务器上其他任务的 CPU 负载影响，建议同时报告评估次数和 token 数作为辅助口径；截断时尚未完成的评估被丢弃，DGM 按代推进，丢弃的工作量多于 HGM；9.646 小时与本机硬件绑定，换机器后只能在同一台机器上比较各方法。

3. 自我改进的一轮迭代

步骤做什么代码位置
① 选父代从已有版本中选一个作为修改对象（HGM 与 DGM 的规则不同，见第 4 节）hgm.py 的 expand()
② 诊断一次大模型调用，不执行代码。随机选一道父代未解出的题，把父代的代码、解题记录、补丁和测试日志交给模型，模型输出"问题在哪、如何改进"的需求描述self_improve_step.py 的 diagnose_problem()
③ 自改把需求描述作为一道编程任务交给父代智能体，修改对象是它自己的代码仓库。改动保存为 model_patch.diff，子代 = 父代 + 该补丁hgm_utils.py 的 sample_child()
④ 评估子代在搜索题上解题。每道题一个容器，内含该题的仓库与工具链以及该子代的代码；智能体结束后放入测试并评分，随后删除容器polyglot/harness.py 的 process_entry()

示例：父代在一道 Rust 题上修改代码后直接提交，从未运行测试。诊断给出"提交前应先运行测试"的需求；自改时父代在自己的主循环中加入这一步，得到"会自测"的子代。它是否更好，由评估决定。

4. 搜索策略：HGM 与 DGM

两者共用同一套框架（初始智能体、诊断、自改、评测和模型均相同），只有搜索规则不同，因此比较的是搜索策略本身。

HGM [1]（hgm.py）DGM [2]（dgm_search.py，在 HGM 框架上重新实现）
调度方式20 个线程异步执行，每一步要么扩展（生成子代），要么评估一道题按代同步：每代选 4 个父代各生成一个子代，全部评估完再进入下一代
扩展时机已完成评估次数 n 满足 n0.6 ≥ 子代数时扩展，否则评估每代固定生成 4 个
父代选择依据整棵子树（节点及其所有后代）的成绩做 Thompson 采样，即论文中的谱系元生产力（clade-metaproductivity）权重 = sigmoid(10 × (准确率 − 0.5)) ÷ (1 + 已有子代数)
评估分配依据节点自身成绩做 Thompson 采样，选中的节点评估一道随机题分段评估：先评 10 题，解出率 ≥ 40% 再评 50 题
档案所有子代都保留在树中生成了补丁且完成 10 题评估的子代进入档案

5. 成本计量

组件作用文件
计量代理容器内的所有模型调用都经过它，记录 token 数以及所属环节、节点和题目。放在智能体之外，因为智能体会改写自己的代码instrumentation/llm_proxy.py
账本所有事件写入同一个 JSONL 文件：模型调用、各阶段耗时、父代选择、子代生成、节点停止。离线实验都以它为数据源runs/ledger.jsonl
GPU 占用小时一次运行的墙钟时间，扣除超过 30 分钟没有任何事件的停机间隔instrumentation/analyze_ledger.py

6. ERL：预测驱动的节点停止

部分说明文件
停止规则子代至少评估 3 题后，若其成绩的 80% 置信上界低于当前最优节点的 5% 置信下界，就停止评估它。被停的节点仍可作为父代；最终选择只依据真实成绩erl/online_stop.py
预测先验预测器给出子代最终解出率 p̂，作为相当于 w 道题的先验并入后验：Beta(1 + 解出 + w·p̂, 1 + 未解出 + w·(1 − p̂))erl/predict_stop.py
特征补丁形态（修改了哪些模块、增删行数）、父代成绩、树中深度、前几道题的结果与耗时；每新增 50 个结果重新训练一次instrumentation/prescreen/predict_from_diff.py
先验权重 w自动校准：只用预测之后才获得的结果检验预测误差，再换算为 w。预测器尚未在本次搜索中得到验证时 w = 0，退化为纯统计规则erl/online_stop.py
在线变体hgm-erlx：停止节省的预算用于生成新子代；hgm-erlxa：另抽取 10% 的停止决定做审计run_all.sh

早期离线回放显示，预测能比纯统计规则节省更多评估，但偶尔会过早停掉真正的最优节点。节省幅度与偶发误判的代价之间如何权衡，仍是开放问题（方向 6）。

7. 开放方向

以下只是起点，欢迎提出自己的问题，或者组合多个方向。

方向核心问题切入点
1. EarlyEval [5] 式单题早停一道题解到一半时，能否根据智能体的行为轨迹判断它注定失败，从而提前终止？instrumentation/early_stop/
2. 小模型代理评估低成本小模型的评估结果，能否预测候选智能体在大模型下的表现与排名？config_local.yaml（更换模型）
3. 下界随迭代的变化随着搜索推进、子代分布漂移，预测器和停止规则是否仍然可靠？账本、erl/replay.py
4. 动态停止阈值停止阈值能否根据剩余预算、当前最优的确定程度等搜索状态自适应调整？erl/policy.py
5. 相邻版本的补丁仅凭子代相对父代的补丁，能否在评估开始前预测它变好还是变坏？各节点的 model_patch.diff
6. 多信号组合多种预测信号如何组合？预测成本、评估节省与误判代价如何权衡？erl/online_stop.py

两个更远的延伸：其一，降低单次评估的成本。让模型自己管理上下文、决定保留什么，可以在长时间的智能体任务上用更少的计算量取得更高的准确率 [13]；我们的一道题最长要跑 1 小时，诊断提示词超长本质上也是上下文管理问题。其二，权重空间的自我改进。已有初步结果显示，大模型可以不经训练、直接读写神经网络权重，作者认为这为 RSI 提供了更直接的路径 [14]；但它超出了本项目"模型固定"的设定，且目前只是博客中的初步报告。

8. 研究约定

约定要求原因
等成本比较与不做预测的基线在相同 GPU 预算下比较最终选出的智能体；报告净节省，即节省的评估成本减去预测本身的成本预测本身也消耗算力（如小模型推理、额外的模型调用）。节省 2 小时评估、预测花费 1.5 小时，净节省只有 0.5 小时
无前视偏差在时刻 t 做出的决定，预测器只能使用 t 之前已经结束的评估来训练和校准离线回放时整份账本都可见，误用之后的数据会让预测显得准确，在线运行时却无法获得这些数据
可消融每项改动通过环境变量开关启用、默认关闭，并记录在 repos/HGM/MODIFICATIONS.md开关关闭时行为与原代码一致，任何人都能用同一份代码做开、关对照（消融实验）
不干扰实验离线分析以最低优先级运行：nice -n 19 ionice -c3 python ...服务器是共享的；GPU 占用小时按墙钟时间计，CPU 和磁盘争用造成的减速会计入正在运行的实验

9. 科学智能体 RSI 探索：换一个科学基准或基线

前面的方法都在 Polyglot 上开发。一个自然的问题是：这些"省评估"的方法换到科学任务上还成立吗？科学任务的一次评估往往更贵（要处理数据、跑分析，甚至训练模型），省评估的收益也可能更大。这一节给出候选的基准、基线和接入路径，具体选哪个、怎么做，由大家自己决定。

9.1 候选基准

基准任务形式评分方式评估成本与接入难度
SciCode [10]科研代码生成：80 个主问题，拆成 338 个子问题，由科学家根据论文结果或解析解编写每个问题都有参考解和单元测试，自动评分成本低，形式与 Polyglot 最接近（写代码、跑测试），最容易接入，适合作为第一站
ScienceAgentBench [11]数据驱动的科研任务：从 44 篇论文中提取的 102 个任务，覆盖生物信息、计算化学、地理信息、心理与认知神经科学智能体输出一个独立的 Python 程序，按程序本身、执行结果和成本评价成本中等，需要准备各任务的数据和运行环境
MLE-bench [12]机器学习工程：75 个离线 Kaggle 比赛，另有 lite 子集对照 Kaggle 排行榜，看是否达到奖牌线成本高：一次评估要训练模型，还会和 vLLM 争用 GPU。正因为评估贵，省评估方法的收益可能最大

9.2 候选基线

科学智能体领域也有递归自我改进的系统，可以作为对照组：

系统搜索与选择方式可以怎么用
AIDE² [6]两层循环：内层按公开指标改实验方案，外层按对内层不可见的隐藏评分选择智能体版本结构与 HGM 最接近，适合作为主要对照
ScienceBuddy [7]只接受在相同任务和种子下配对评估得分提高、且满足编辑约束的修改；之后再训练模型只取它"改流程"的部分作对照（本项目模型固定）
RHI [8]新产物与缓存的上一版产物两两比较，新版胜率低于阈值时停止整个改进它的停止条件可以作为"整个搜索何时结束"的基线
AI Scientist-v2 [9]分阶段的实验树搜索，节点分为调试、改进、复验等类型它搜索的是实验方案而非智能体本身，适合在任务层面对照

这些系统的代码是否开源、能否换成我们的本地模型，需要先确认。如果直接跑原系统不现实，可以像 dgm_search.py 那样，只把它们的搜索与选择规则在我们的框架上重新实现，这样比较的就只是策略。

9.3 接入路径

步骤做什么参照
① 评测程序为新基准写数据准备和评分：每个任务一个容器，运行智能体，再按基准的规则评分，并在各阶段打上计量时间点repos/HGM/polyglot/（prepare_polyglot_dataset.py、harness.py）
② 检查泄露确认智能体在容器里看不到参考解和测试，例如 SciCode 的参考解HGM_HIDE_ANSWERS 的做法（polyglot/test_spec.py）
③ 划分任务分出搜索集和留出集，留出集只用于最终评估polyglot/subsets/
④ 测初始智能体测单次评估的成本，以及重复评估的噪声，据此定预算repeat_eval.py、instrumentation/repeat_stats.py
⑤ 等成本对照在相同 GPU 预算下跑 HGM、DGM、ERL，以及选定的科学基线run_all.sh（新增配置）

计量代理和账本与基准无关，接入新基准后照常工作。这些科学 RSI 工作在评估设计上也有可借鉴之处，例如修改前先做有效性检查、按评分细则给部分分 [7]、优先在父代已评过的任务上做配对比较 [7, 8]、把指导修改的信号与选择版本的信号分开 [6]，都可以在新基准上一并尝试。
